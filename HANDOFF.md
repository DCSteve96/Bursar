# Bursar: project state and decisions (handoff, started 20 October 2026)

Working notes of the team, translated from Italian. Not written for judges; kept for whoever continues the work.

This file passes to Claude Code everything that was decided and verified in chat. It is not for the judges. When something here changes, update this file.

## 1. The project on one page

Problem: companies pay fake invoices ("new bank details" fraud, the most widespread business scam) and duplicate invoices. An AI that pays invoices makes both worse, unless it never has the keys.

Solution: the agent reads the invoice in a TEE and asks the contract to pay with a single key limited to `request_payment`, without owning NEAR (meta transaction). The contract decides: vendor on the allowlist, payout on the invoice equal to the one registered by the owner, no duplicates, caps per payment, monthly per vendor and daily, DAO approval above a threshold. It pays on NEAR in the same transaction, or queues the payment for the executor, which uses NEAR Intents towards the vendor's chain (the contract checks that the recipient is the registered one). Everything is an on-chain event; no database.

Tracks: `realworld` (main), `business`, `privacy`, `security`. Name: Bursar (to be confirmed, it must be unique in the hackathon).

### 2.1 Done in the cloud session of 20 October (offline only: the container network blocked NEAR RPC, NEAR AI and Intents)

- Contract: callback on `add_proposal` that saves `dao_proposal_id` (event `dao_proposal_opened`) and, if the DAO refuses to open the proposal, blocks the payment with `dao_proposal_failed` and frees the budget. New method `sync_dao_proposal(id)` (anyone can call it): reads `get_proposal` from the DAO and, only on the DAO's answer (`Rejected`, `Expired`, `Removed`, `Failed`, `Moved`), cancels the payment with reason `dao_<status>`. Callback `on_ft_transfer` on every `ft_transfer`: if it fails, the balance comes back (`Paid` -> `Blocked transfer_failed`, `Settling` -> `Queued`, withdraw restored). 11 unit tests. Public signatures unchanged (no change to `near.ts`), only new methods.
- Wasm: `strip = true` in the release profile takes the wasm from 502 KB (with the callbacks) to 303 KB; with `wasm-opt -Oz` 249 KB. `contracts/policy/build.sh` applies wasm-opt if present. The contract must be redeployed (the state structures did not change, `Payment.dao_proposal_id` already existed).
- `ai.ts` no longer uses the OpenAI SDK: it calls the API with `fetch` and keeps the exact bytes of request and response, because the gateway signs `<model>:<sha256(req)>:<sha256(res)>` over the bytes, and a reserialization broke the signature. The receipt in `.bursar/receipts/<id>.json` contains everything: bytes, signature, attestation report with TDX quote, nonce.
- `verify.ts` and `bursar verify <id>`: independent verification without an API key. Checks: hash of the bytes, signed text, ECDSA recovery (EIP-191, like `ethers.verifyMessage`), `signature_kind == provider_tee`, report with the same signer and our nonce, `report_data` of the TDX quote (signer in bytes 0..20, nonce in bytes 32..64), quote verified against the Intel collateral with `@phala/dcap-qvl` (network needed, `--no-collateral` to skip), extraction identical to the model output, `attestation_ref` on chain. Formats taken from the source of `@nearai/inference-sdk` 0.1.0 (which requires Node 24, which is why we do not use it). It does not yet replay the event log on RTMR3 nor verify the GPU.
- App tests with vitest (`npm test`): signature recovery on a known vector, tampered receipt (modified response, signature from another key, different nonce, gateway signature), offline parser on the 4 invoices.
- `bursar sync` and MCP tools `sync_dao_approvals`, `verify_attestation`; the executor calls `syncApprovals` at every tick and skips Intents outside mainnet.
- Static dashboard `web/index.html`: reads the contract via RPC, no build.
- README updated with the "do X, see Y" steps for verify, sync, dashboard, tests. The example outputs of `verify` are the command's format, not a real run: to be redone with a real receipt.

### 2.10 Reading relay and two plans (20 October, same session)

The maintainer: the NEAR AI key must not be an obstacle, and the relay is the approach also for when we resell the product; better still, two plans.

- `relay/worker.js`: Cloudflare Worker that holds the NEAR AI key (secret `NEAR_AI_API_KEY`) and forwards three routes, `POST /v1/chat/completions`, `GET /v1/attestation/report`, `GET /v1/signature/{id}`, without touching the bytes (the enclave's signature is over the sha256 of request and response, so the relay cannot reserialize). Constraints: a single allowed model, no streaming, body up to 2 MB, origin allowlist (`ALLOWED_ORIGINS`, default `https://dcsteve96.github.io`), daily limits per IP and in total if the KV `LIMITS` is there (20 and 300). `wrangler.toml` and a README in the folder with the steps from the Cloudflare dashboard (no installation on the Mac).
- Console: "Reading" field with two choices, "Bursar reading (included)" and "My own NEAR AI Cloud key"; the key field appears only with the second. ## 3. Decisions taken

- Monetization (future, not for the hackathon): fee in bps in the contract, Intents `appFees` (already provided for in the code with `referral: "bursar"`), subscription for the hosted part (reading, relayer, export), NEAR grants. Not a payment service.
- Hosted part, boundary to keep (reasoning of 20 October, to be confirmed with the maintainer): we can host the agent (key limited to `request_payment`, no spending power), the relayer (pays only gas, an account of ours), monitoring, notifications, export, connectors. The executor key with the power to `settle` must not be hosted: even if the contract binds the recipient, it is the only key that makes USDC leave, and holding it ourselves looks like custody. If one day it is needed, the executor key becomes a function-call key limited to `settle` and `mark_settled` on the company's contract (the contract already checks the recipient), and it stays in the company's hands anyway. This is not legal advice.

## 5. Verified APIs (source: official docs, 19-20 October)

### NEAR AI Cloud
- Response signature (verified in the source of SDK 0.1.0): `text` = `<canonical model id from the request>:<sha256 hex of the request bytes>:<sha256 hex of the response bytes>`; `signature` ECDSA 65 bytes, verified with `ethers.verifyMessage` (EIP-191) and compared with `signing_address` (20 bytes). `signature_kind` `provider_tee` = signed in the model's TEE; `gateway` = signed by the gateway (when it rewrites the response), does not prove execution in the model's TEE. `GET /v1/attestation/report` answers `{ model_attestations: [ { request_nonce, signing_algo, signing_address, intel_quote (hex), event_log, info, nvidia_payload?, report_data? } ] }`; in the TDX quote `report_data` = signer (20 bytes, zero-padded to 32) + nonce (32 bytes). Signatures stay on the gateway for 60 minutes: `fetchSignature` must be called right after the completion, as `ai.ts` does.
- Base URL `https://cloud-api.near.ai/v1`, OpenAI compatible. Key from cloud.near.ai (prepaid credits, spend limit per key).
- Models in TEE with vision: `z-ai/glm-5.3-flash` (chosen, structured outputs, 1M ctx, cheap), `Qwen/Qwen3.8-27B`, `Qwen/Qwen3-VL-30B-A3B-Instruct`. No PDF as input: rasterize with `pdftoppm` and send base64 PNG in `image_url`.
- Attestation: `GET /v1/attestation/report?model=<id>&provider=near&signing_algo=ecdsa&nonce=<32 byte hex>` with header `x-no-aliasing: true`, to be called before the completion. Response signature: `GET /v1/signature/<completion id>?signing_algo=ecdsa` returns `text`, `signature`, `signing_address`, `signature_kind` (`provider_tee` = `<model>:<sha256(req)>:<sha256(res)>`). Use non-streaming requests with the canonical model id. Alternative SDK: `@nearai/inference-sdk` (Node 24+).
- `ai.ts` saves `inference_id`, hashes of request and response, nonce, `signing_address` and puts a compact reference in the payment's `attestation_ref`.

## 2.30 Readable contract errors (21 October)

- Bug found by the maintainer: "Add purchase order" without a reference gave `WebAssembly trap: unreachable` instead of "a purchase order needs a reference". Cause: with rustc 1.97 and near-sys 0.3 (`unsafe extern "C" { fn panic_utf8(..) -> !; }`) the compiler removed the call to `panic_utf8` and left a silent trap: the wasm did not even import `panic_utf8` (`strings bursar_policy.wasm | grep panic_utf8` -> 0). This applies to all contracts compiled so far, so also today's treasuries: their failed checks stay silent.
- Fix in `lib.rs`: own declaration of `panic_utf8` without `!` (`mod host`), `fail(msg) -> !` that calls it and then `loop {}`, and a crate `require!` that uses `fail`; `require` is no longer imported from near_sdk. Verified on chain on `bursar-panic-94f66172.testnet`: "Smart contract panicked: a purchase order needs a reference", "unknown vendor". The SDK's internal panics (deserialization) stay traps. 24 tests, wasm 386402.
- Console: `txFailureText()` translates the Failure into words ("the contract refused it: ..."; for old contracts "one of its checks failed"); the purchase order form checks reference and amount before calling. Older toolchains (1.86) do not compile the dependencies (edition 2024): no downgrade.

## 2.33 sync_balance (21 October)

The stress test showed that a USDC deposit made with a simple `ft_transfer` (wallet, exchange) does not go through `ft_on_transfer` and the contract does not see it. Added `sync_balance()` (owner or any operator): calls `ft_balance_of` on the token and in the callback `on_sync_balance` sets `balance = held - in_flight`. `in_flight` is the sum of the transfers sent whose callback has not arrived yet: incremented in `ft_transfer` (the internal helper used by payments, settle, withdraw), decremented in `on_ft_transfer` on every outcome; it lives in raw storage (`b"inflight"`, like the vault) so already deployed contracts update without migration. Event `balance_synced` with old:new:in_flight. 26 tests (two new: count with money in flight and failed transfer; outsider rejected). wasm 386402.

Console: in Overview, if `ft_balance_of(treasury)` on the token exceeds `get_stats().balance`, the line "The USDC contract holds X more..." appears with the Sync balance button (enabled with the owner's or an operator's key). Verified on chain on `treasury.bursar-sync-d542af4c.testnet` (1000 with ft_transfer_call, 500 with simple ft_transfer: books 1000, token 1500, after sync 1500; outsider rejected with a readable message) and in the console with Playwright. README step 9f.

## 2.34 Security audit of the contracts (21 October)

Requested by the maintainer ("full audit, several times"). Method: complete reading by me, four independent reviewers in parallel with different angles (permissions and roles; accounting and asynchrony; policy logic; storage, gas, registry and token), then a second round with two fresh reviewers on the corrected code. Every accepted finding has an `audit_*` test that reproduces it (it failed before, passes after). 50 tests, wasm 418314 bytes (+31 KB for indexes and new methods; serde_json avoided with a hand-written escape in the events).

Found and corrected in the policy contract:
- Approval of a held payment even after pause or deactivation of the vendor: `approve_payment` rechecks pause, active vendor and payout.
- Executor: `settle` checked the declared recipient but the funds went to the `deposit_address` chosen by the executor. Now the owner registers the Intents deposit account (`set_settlement_account`, raw key `settle_to`) and the executor can pay only that one or a sub-account of it; `settle` respects pause and active vendor; `mark_settled` and `mark_settlement_failed` wait for the transfer callback (`in_flight == 0`).
- Payout reread at payment time: an operator with the vendors role could change the payout between the request and the approval and divert the money, even beyond the DAO. Now every accepted payment saves the payout it was checked against (`ps`+id) and `execute`/`settle` refuse if the vendor has a different one; a payout registered or changed by a non-owner marks the vendor `pu`+id: hold `payout_unconfirmed`, approval and settle refused until the owner calls `confirm_vendor_payout`.
- `release_reservation` decremented the current day and month even for reservations from earlier days (daily cap and monthly budget could be inflated by cancelling old holds): now it compares day and month of `created_at` with those of the counters.
- The withheld tax was inside the spendable balance: `spendable() = balance - withheld_due` in decide/execute/settle/withdraw; `remit_withholding` sends the withholding to the owner and clears the debt together (callback `on_remit` restores both if it fails); `mark_withholding_remitted` stays for those who paid the state from outside.
- Compromised agent: claim fields limited (`check_claim_size`), daily quotas in raw storage for non-owners (500 requests, 200 refusals, 50 holds), `dao_bond_missing` if the account has no NEAR for the bond plus 1 NEAR of margin, `many_invoices` after 5 invoices from the same vendor paid without a person in the day.
- Duplicates: normalized number (only letters and digits, uppercase) and index by file hash (`ih`+hash); old key still checked; `no_invoice_identity` without number or hash.
- Orders: index per vendor (`vo`+id, at most 64 open), vendor "bound to orders" (`vb`) even after the last one is closed, `set_order_bound` to remove the binding; `period_days <= 3660` (overflow); `list_payments` iterates over the ids.
- Settling with no way out after an Intents refund: `mark_settlement_failed` puts it back in the queue (executor or owner); the executor calls it on REFUNDED/FAILED.
- `in_flight` stuck if a callback does not run: `reset_in_flight` (owner); `GAS_CALLBACK` 30 TGas; memo without invoice number; DAO proposal with 80 TGas.
- `clear_dao`; `sync_dao_proposal` checks the DAO on which the proposal had been opened (`pd`+id); `transfer_ownership` rejects agent, executor and the treasury itself and removes the new owner from the operators; `add_operator` requires at least one role; `set_limits` rejects zero caps; `same_as` ignores case only for 0x addresses; events with JSON escaping; `vendor_state` and `get_in_flight` as views.
- My own error found by the live test: the orders index wrote to storage inside `preview_payment` (a view): now the views only read, the index is written when an order is added or closed.

Registry: index per owner in raw storage (`o`+owner, `reindex` for old entries), `claim(treasury)` which asks the treasury for `get_roles` and accepts only the contract's answer (whoever squatted an entry loses it), `list` at most 100, readable error messages (`fail` shim). 5 tests. To be redeployed by the maintainer: the key of `registry.bursar-b48563e6.testnet` is not in this session. Test token: `mint` at most 1.000.000 tUSDC per call and a supply cap (a single mint at u128::MAX blocked the faucet forever). To be redeployed by the maintainer.

Web: explorer and login accept a registry entry only if the hash of the treasury's code is in `web/contracts/builds.json`; console with the new reasons, vendor state (payout to confirm, order binding), settlement account in the settings, remittance of the withholding with `remit_withholding` (fallback to the old method), note and reset of the money in flight. MCP and executor updated.

Second round (two fresh reviewers on the corrected code). Found and corrected: `mark_settlement_failed` (my correction from the first round) allowed the executor to put a payment back in the queue without a refund and pay it again until the balance was emptied: now it is a cross-contract call, the callback `on_settlement_failed` puts it back in the queue only if `ft_balance_of` shows the refund on the account (`held >= balance + net`) and counts the balance in the same step; quotas per caller (no longer global: a flooding agent does not block the operators); no registration while paused; refusals saved small (2 flags, 64 bytes of attestation and hash); DAO proposals opened by the contract at most 10 per day per non-owner key, never for a payout to confirm, never without NEAR for the bond, and `open_dao_proposal_for` (owner or approver) for the holds left without a proposal; settlement account with at least one dot (a top-level name would make every account valid); agent and executor never operators; withholding restored only in the Paid and Settling branches of the callback; per-payment keys (`ps`, `pd`) removed when the payment can no longer move; `list_payments` with saturating `from`; `preview_payment` reflects the holds quota. 51 tests. Client side: relayer with a cap of 150 TGas and an hourly limit (RELAYER_MAX_PER_HOUR, 300); `readingFlags` checks the amount the claim will carry (`claimValues`), not the model's decimal; claim fields cut to the contract's limits (`CLAIM_LIMITS`, `clip`) in agent and console; vendor chosen by id or exact name, then by tax id, then by a single partial match flagged with `vendor_ambiguous`; agent that retries failed files three times and then parks them in `inbox/failed`; console with the "Open proposal" button for holds without a proposal and explicit confirmation before saving an empty daily cap.

Residual risk declared by the second round (unchanged by choice): with all the limits, a stolen agent key can pay fake invoices to registered vendors for at most 5 invoices below the threshold per vendor per day, within the daily cap and the monthly budget, always and only to the registered payouts; anyone who manages to deliver a well-made PDF (name, payout and tax id are public) gets the same effect, so purchase orders are the defence for those who want to close this too; the windows are UTC days and months (doubling around midnight); the executor stays trusted for the recipient declared in the quote within the settlement account: to verify on mainnet what 1-Click returns as the deposit address and whether a deposit of `net` in EXACT_OUTPUT is accepted (executor.ts quotes `amount`, the contract sends `amount - withheld`).

Accepted and documented, not changed: the approval threshold is per invoice (5 invoices per day per vendor without a person, then hold; the daily cap stays the real limit); the flags and tax ids of the claim come from the reading and can only add checks; the executor is trusted for the queued amounts within the settlement account; queued and held payments do not reserve the balance (over-commitment: `settle`/`approve` fail with a clear message); a deposit `ft_transfer_call` that arrives while a `sync_balance` is running can be counted twice until the next sync. Already deployed contracts (demo, the maintainer's treasuries) stay on the old wasm until they are redeployed with the treasury's key: the state is compatible, no migration.

## 2.46 Web wallets blocked by the CSP (30 October)

The maintainer: choosing Meteor (without the extension), Intear or the other wallets in the picker of login.html, "Wallet executor \"Meteor Wallet\" did not initialize within 5s". Cause: the CSP with hash-based `script-src` put in during the third audit. NEAR Connect downloads the code of the wallet's executor and injects it into an iframe with `srcdoc` (hot-connect.es.js, `this.iframe.srcdoc = o`); a srcdoc iframe inherits the page's CSP, so the wallet's inline script was refused and the executor never answered. The Meteor extension does not go through the iframe, which is why it worked. The script-src cannot be kept: with hashes present browsers ignore `unsafe-inline`, and the wallets cannot be enumerated. Done: `web/csp.py` now writes only `object-src 'none'; base-uri 'self'; form-action 'self'` on console.html and login.html (the CDN imports stay protected by `integrity` in the import map); README corrected in the paragraph on the third audit. Playwright verification: an inline script in a srcdoc iframe runs; in the real picker choosing Meteor reaches "[near-connect] wallet-ready received" without error. The console uses the same NEAR Connect for the signatures of wallet owners: it had been broken in the same way since 24 October, now it is not.
